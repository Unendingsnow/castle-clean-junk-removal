1. HOW THIS WAS TESTED
================================================================================
Outbound calls to api.telegram.org were wrapped with an interceptor loaded via
NODE_OPTIONS, so every request the app made was captured in full before it left
the process. That made it possible to verify the ACTUAL bytes sent to Telegram
(escaping, attach:// wiring, field ordering, topic routing) rather than
inferring correctness from HTTP status codes.

The interceptor ran in four modes:
  passthrough  real delivery to the live group (used for the 6 end-to-end sends)
  mockok       valid response without calling Telegram (used for the 51-test
               adversarial run, so probe traffic didn't flood a real group)
  fail/http500/malformed/slow   simulated upstream failures

Each adversarial request carried a unique X-Forwarded-For so the per-IP rate
limit didn't mask unrelated results. Whether that spoofing works was itself one
of the tests (see FINDING-01).

2. DEFECT FOUND AND FIXED
================================================================================

FIX-01  DUPLICATE SUBMISSIONS ON RAPID CLICKS                    [FIXED]
--------------------------------------------------------------------------------
Severity        HIGH — customer-visible, revenue-affecting
Found by        Browser test: triple-click on the submit button
Status          Fixed and re-verified in this run

WHAT HAPPENED
  Clicking submit three times quickly fired THREE separate POST requests.
  Measured directly by counting network calls in the page.

  The guard `if (busy) return` reads React state. State does not re-render
  within the same event-loop tick, so the second and third clicks both saw
  busy === false and passed straight through.

REAL-WORLD IMPACT
  1. Three identical leads arrive in Telegram from one customer. David calls
     the same person three times, or quotes a job twice.
  2. Worse: it consumes all three of that customer's rate-limit slots. If the
     submission then fails for any reason, their genuine retry is blocked with
     "You've sent a few requests already" — and the business loses the job.

  This was observed live during testing: the triple-click test exhausted the
  quota, and the very next legitimate submission from that browser was
  rejected with a 429.

  Impatient double-clicking on a submit button is one of the most common
  real-world user behaviours there is. This would have happened in week one.

FIX APPLIED
  Replaced the state-based guard with a ref, which updates synchronously:

    const submittingRef = useRef(false);
    if (busy || submittingRef.current) return;
    ...
    submittingRef.current = true;   // set before the first await
    ...
    } finally { submittingRef.current = false; }   // released on every path

VERIFIED
  Five rapid clicks -> exactly 1 network POST. Success panel renders normally.
  Retry after a failure still works (guard released in `finally`).

FINDING-01  RATE LIMIT BYPASSABLE VIA X-FORWARDED-FOR
--------------------------------------------------------------------------------
Severity        LOW in production / MEDIUM if ever self-hosted
Status          Accepted — behaves correctly on Vercel

  Six requests with rotating X-Forwarded-For headers: 0 blocked.
  Six requests with a fixed header: rate limit engaged correctly after 3.

  The limiter trusts X-Forwarded-For, which a client can set freely when
  talking to the server directly.

  WHY THIS IS OK ON VERCEL: the platform overwrites X-Forwarded-For at the
  edge, so a client cannot forge it. The header is only spoofable when the app
  is reached directly, which does not happen in the intended deployment.

  WHEN IT WOULD MATTER: self-hosting behind a misconfigured proxy, or any
  future move off Vercel. If that happens, switch to a platform-verified
  identifier and treat the header as advisory.

  Also inherent: the limiter is in-memory and per-process. On a scaled-out
  deployment the effective limit is 3 x (number of live instances). It stops
  casual spam, not a determined attacker. Already documented in the README.


FINDING-02  UPLOAD MIMETYPE IS TRUSTED, CONTENT IS NOT SNIFFED
--------------------------------------------------------------------------------
Severity        LOW
Status          Accepted — no practical attack path

  A file containing PHP source, sent with Content-Type: image/jpeg, was
  accepted and forwarded to Telegram.

  WHY THIS IS NOT EXPLOITABLE HERE:
    - Uploads are never written to disk on the server
    - They are never served back to any browser
    - They go straight to Telegram, which does its own validation and will
      reject a non-image with "IMAGE_PROCESS_FAILED"
    - Filenames are discarded and regenerated server-side, so a malicious
      filename cannot influence anything

  Confirmed rejected by mimetype allowlist: SVG (a real XSS vector) and
  executables. Magic-byte sniffing would be defence in depth, not a fix for a
  live hole.

================================================================================
5. NOT COVERED
================================================================================
Stated plainly so the gaps are known:

  - Real iOS/Android browsers. Testing used headless Chrome with device
    emulation. Safari's HEIC handling in particular is untested; iPhones
    normally convert to JPEG on upload, but this has not been confirmed on a
    real device.
  - Vercel's 4.5MB serverless request body limit. Cannot be reproduced
    locally. Eight resized photos is roughly 2MB so normal submissions fit,
    but a customer sending eight unusually detailed photos could exceed it and
    see a platform error before the route runs.
  - Sustained abuse over hours, or distributed flooding from many IPs.
  - Telegram's own rate limits under heavy real traffic (~20 messages/minute
    per group). At 50 leads a week this is not close to a concern.
  - Email deliverability — there is no email sending in this system.
